# Desktop / no-phone build

AR_Horizon has two runnable surfaces:

- **Android app** — camera, ARCore, sensors, offline packs.
- **Desktop field simulator** — the same pack, horizon and labels in a browser,
  no phone, no emulator, no server.

This exists because the terrain maths and label behaviour should be testable
without owning ARCore hardware, and because a browser is the cheapest demo
surface for the project.

![Desktop field simulator](goldens/desktop-simulator.jpg)

## Run it

```powershell
# Zero server: open the file directly.
Start-Process web\index.html
```

Or serve it locally:

```powershell
web\serve.ps1          # http://127.0.0.1:8099
```

Everything is embedded in `web/data.js` (about 2 MB). There is no fetch, no API
and no external font or library. It works offline from `file://`.

Controls:

- **drag** to pan
- **scroll** to zoom (24°–100° horizontal FOV)
- **click a label** for distance, bearing, elevation and hidden state
- **Viewpoint** switches between Gornergrat (west), Gornergrat north-east,
  Zermatt and Breuil-Cervinia
- **Hidden on/off** toggles the dimmed ridge-blocked labels
- **Features** lists the current labels by bearing
- **About** explains the simulator and attribution

## What it shares with the app

Generated by `tools/export_web.py` from `alps.pack.sqlite`:

- the same 1" / 4" DEM, sampled into 3,600 azimuth bins;
- the same curvature drop `d²/(2·R_eff)` and 0.03° visibility bias;
- the same distance/type LOD rules;
- the same type/population/rank/proximity score and 35-label cap;
- the same label styles: white peaks with elevation, amber towns, blue italic
  water, muted landmarks, dimmed hidden labels.

The browser renderer uses a mirrored pinhole projection, not the compiled C++
core. The core and the Python silhouette match to 5×10⁻⁵° across all bins, and
the synthetic lock test uses the compiled C++ `vt_fit_skyline`.

## Regenerate

```powershell
.\.venv\Scripts\python.exe tools\export_web.py
```

It reads the pack, computes full/40 km/13 km silhouettes for four viewpoints and
writes `web/data.js` and `web/data.json`. Re-run after rebuilding the pack.

For any other coordinate inside the pack, render a still from the command line:

```powershell
.\.venv\Scripts\python.exe tools\render_golden.py `
  --lat 45.98331 --lon 7.78470 --heading 265 --pitch 4 --fov 72 `
  --out docs/goldens/custom.png
```

It uses the same pack, horizon and label rules as the app and writes a PNG plus
a JSON label record.

## Synthetic skyline lock — no camera

```powershell
core\build_core_dll.bat
.\.venv\Scripts\python.exe tools\validate_skyline_lock.py
```

This builds a small C-ABI DLL, generates camera-like frames from the DEM horizon
with a deliberately wrong reported heading, runs the **same 160×120 boundary
extractor** as `SkylineSampler.kt`, and calls the **same C++ fit** as the app.

Latest result:

| Injected yaw error | Recovered | Error | Score |
|---|---|---|---|
| +4.00° | +3.95° | 0.05° | 0.950 |
| -3.20° | -3.20° | 0.00° | 0.948 |
| 0.00° | +0.05° | 0.05° | 0.956 |
| +7.10° | +7.20° | 0.10° | 0.971 |
| -7.80° | -7.85° | 0.05° | 0.956 |

Proof image: `docs/goldens/skyline-lock.png`.
Machine-readable result: `docs/goldens/skyline-lock.json`.

What this does **not** test: actual camera exposure, rolling shutter, motion
blur, ARCore pose timing, or the magnetometer seed. Those still need a phone.
It does prove that a DEM skyline, a real image boundary and the yaw fit can
recover a known offset to within 0.1°.

## Limits

- One pack, four fixed viewpoints. It is a field simulator, not the pack manager.
- No camera feed and no AR tracking; those are Android-only.
- Browser labels are a mirror of the core solver, not the compiled solver.
- It is deliberately a static artifact: no accounts, no analytics, no calls home.
